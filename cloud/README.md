# NEXO CLOUD PRIVATE

لوحة خاصة لإدارة بوتات Discord المبنية بـ Node.js. ملفات المشروع محفوظة في GitHub، لكن GitHub ليس خادماً لتشغيل البوتات: جعل المستودع Private يحمي الكود من العرض العام فقط، ولا يشغّل الموقع أو البوتات 24/7.

## الموجود حالياً
- دخول خاص بكلمة مرور `HOST_PASSWORD` وجلسة HttpOnly.
- رفع ZIP مع حدود للحجم وعدد الملفات وفحص المسارات، ورفض الروابط الرمزية وأنواع الملفات الخاصة والمسارات غير الآمنة، مع اشتراط وجود `index.js` كملف فعلي في الجذر.
- عرض البوتات وحالتها، وتشغيلها وإيقافها وإعادة تشغيلها من اللوحة.
- عرض آخر سجلات كل بوت.
- تثبيت مكتبات البوت من `dependencies` في `package.json` مع تعطيل `install scripts`، والتحقق من أسماء المكتبات وإصداراتها، وحد أقصى 40 مكتبة ومهلة 3 دقائق، وبحد أقصى عمليتين للتثبيت في الوقت نفسه.
- حماية إضافية لطلبات لوحة التحكم: فحص `Origin` لطلبات التغيير، تحديد معدل الطلبات، وتحديد الرفع إلى 5 ملفات خلال 10 دقائق.
- تطبيق تحديد معدل الطلبات وفحص المصدر أيضاً على واجهات API القديمة، وإخفاء ترويسة تعريف Express.
- إيقاف البوت بإرسال الإشارة إلى مجموعة عملياته على Linux، ثم التصعيد إلى `SIGKILL` بعد مهلة إذا لم يتوقف.
- حماية الجلسات: كلمات مرور لا تقل عن 16 حرفاً، جلسات عشوائية HttpOnly وSameSite=Strict، حد أقصى 1000 جلسة، وتسجيل خروج يبطل الجلسة.
- رؤوس حماية المتصفح عبر Helmet وContent Security Policy، ومنع تخزين استجابات API في الذاكرة المؤقتة.
- حدود تشغيل افتراضية: 5 بوتات تعمل في الوقت نفسه و20 بوتاً مخزناً، مع إمكانية تغييرها بمتغيرات البيئة.
- صلاحيات مجلد البوتات 700 والملفات المرفوعة 600، مع حد فعلي للحجم بعد فك ZIP وليس اعتماداً على بيانات الأرشيف فقط، وإخفاء قيم متغيرات البيئة من السجلات عند تطابقها.
- تشغيل تلقائي بعد إعادة تشغيل الخادم للبوتات التي تم تشغيلها من اللوحة.
- تشغيل البوتات وتثبيت مكتباتها داخل `bubblewrap` على Linux، مع namespaces منفصلة للعمليات والملفات وIPC وUTS، وبيئة ملفات مقيدة للقراءة فقط باستثناء مجلد البوت و`/tmp` المؤقت. الشبكة مشتركة للسماح باتصال Discord.
- حدود موارد مستقلة لكل بوت عبر cgroups v2: RAM افتراضياً 512MiB، CPU افتراضياً 50% من نواة واحدة، و64 عملية كحد أقصى. يمكن تعديلها بمتغيرات البيئة.
- متغيرات بيئة منفصلة لكل بوت، تحفظ في ملف `.nexo-env.json` بصلاحيات ملفات مقيدة.

## تشغيل المنصة
يلزم خادم Node.js يعمل باستمرار؛ لا يكفي فتح المستودع في GitHub. إعدادات التشغيل:
- إصدار Node.js المقترح: 22.
- مجلد المشروع: جذر المستودع.
- أمر تثبيت حزم المنصة: `npm install`.
- أمر التشغيل: `npm start`.
- متغير البيئة المطلوب: `HOST_PASSWORD`، ويجب تعيين كلمة مرور قوية وفريدة لا تقل عن 16 حرفاً من لوحة الخادم، لا داخل GitHub.
- متغيرات اختيارية: `NEXO_MAX_RUNNING_BOTS` (افتراضياً 5، أقصى قيمة 20)، `NEXO_MAX_BOTS` (افتراضياً 20، أقصى قيمة 100)، و`TRUST_PROXY=true` فقط إذا كان التطبيق خلف وكيل عكسي موثوق واحد.
- المنفذ: يستخدم المشروع قيمة `PORT` التي توفرها الاستضافة، أو 3000 عند التشغيل المحلي.
- يجب أن تكون مساحة `/app/bots` أو المجلد المحدد في `NEXO_BOTS_DIR` دائمة التخزين حتى لا تضيع ملفات البوتات عند إعادة إنشاء الخادم.

بعد تشغيل خادم Node.js، تفتح لوحة التحكم من نفس عنوانه على المسار `/cloud`. واجهة Wispbyte الثابتة الحالية ليست محرك التشغيل ولا يمكنها وحدها تشغيل هذا الخادم.

## حدود الأمان وتجهيز الخادم

NEXO يرفض تشغيل البوت أو تثبيت مكتبته إذا لم يجد إعداد العزل كاملاً. يلزم Linux مع:
- `bubblewrap` مثبت ويستطيع إنشاء user/PID/mount namespaces.
- cgroups v2 مع تفويض متحكمات `cpu` و`memory` و`pids` إلى خدمة NEXO.
- مجلد البوتات على تخزين دائم، ومستخدم نظام مخصص غير root.

أضفنا قالب خدمة systemd في `deploy/nexo-cloud.service`. القالب يشغل التطبيق كمستخدم `nexo` ويطلب تفويض متحكمات cgroups. قبل تشغيله، جهّز مستخدم `nexo`، وضع المشروع في `/opt/nexo`، وأنشئ `/etc/nexo/nexo.env` بصلاحيات مقيدة وفيه كلمة مرور قوية. جهّز مجلد البيانات `/opt/nexo/bots` واجعله مملوكاً للمستخدم `nexo`. بعد مراجعة القالب وتعديل المسارات حسب الخادم:
1. انسخ `deploy/nexo-cloud.service` إلى `/etc/systemd/system/nexo-cloud.service`.
2. فعّل الخدمة: `sudo systemctl daemon-reload && sudo systemctl enable --now nexo-cloud`.
3. تحقق من وجود الملفات `cpu.max` و`memory.max` و`pids.max` داخل مجلد cgroup الخاص بالخدمة، ومن نجاح تشغيل `bwrap` بدون أخطاء.
4. لا تفتح اللوحة للإنترنت قبل وضعها خلف HTTPS وإتمام اختبارات العزل.

الحدود الافتراضية لكل بوت: RAM `512 MiB`، CPU `50%` من نواة واحدة، و`64` عملية. مجلد `/tmp` داخل العزل محدود إلى `128 MiB`. غيّر حدود cgroups عبر `NEXO_BOT_MEMORY_MAX` (بايت)، `NEXO_BOT_CPU_PERCENT` (نسبة مئوية)، و`NEXO_BOT_PIDS_MAX`. لا توجد حتى الآن حصة قرص صلبة لمجلد `/workspace`؛ لذلك لا تعتبر مساحة التخزين محمية بحصة لكل بوت.

**مهم:** هذا إعداد عزل قوي أولي وليس شهادة أمان لاستضافة كود عدائي. الشبكة مشتركة ومفتوحة لخدمات Discord، ولا توجد حتى الآن سياسة خروج شبكي تمنع الوصول إلى عناوين داخلية/خاصة، كما لا توجد حصة قرص صلبة لكل بوت. يجب اختبار kernel وcgroups وbubblewrap على الخادم الفعلي. لا تستخدم Docker Compose الحالي لاستضافة بوتات غير موثوقة؛ إعداد cgroup delegation وuser namespaces داخله غير مجهز تلقائياً، وسيُرفض التشغيل إذا لم تتوفر المتطلبات.
## فحص الخادم قبل التشغيل

بعد تجهيز خدمة systemd وتشغيلها كمستخدم `nexo`، نفّذ:
```bash
sudo -u nexo NEXO_CGROUP_ROOT=/sys/fs/cgroup/system.slice/nexo-cloud.service NEXO_BOTS_DIR=/opt/nexo/bots bash /opt/nexo/deploy/host-security-check.sh
```
الفحص يتأكد من Linux وBubblewrap وcgroups v2 ويفحص وجود خيار project quota على نظام الملفات. وجود خيار quota وحده لا يعني أن حصة كل بوت طُبقت؛ لذلك لا ترفع أكواد مستخدمين قبل إعداد وتفعيل project quotas فعلياً والتحقق من الحد على ملف تجريبي.

### فلترة الشبكة

قالب systemd يضيف `IPAddressDeny` لحظر IPv4 private/loopback/link-local/CGNAT وIPv6 loopback/ULA/link-local عن الخدمة وكل عملياتها التابعة، مع استثناء DNS المحلي الشائع `127.0.0.53` و`127.0.0.11`. هذه سياسة على خدمة NEXO كلها وليست عزلاً شبكياً مستقلاً لكل بوت؛ عدّل استثناء DNS إذا كان الخادم يستخدم عنوان DNS مختلفاً. يجب اختبار حظر عناوين الشبكة الداخلية فعلياً بعد تشغيل الخدمة، لأن دعم مرشح systemd يعتمد على kernel وcgroup BPF.

**حالة مهمة:** لم نضف بعد تطبيقاً آلياً لحصة قرص صلبة منفصلة لكل بوت، ولم يُجر اختبار حي على خادم Linux. فحص GitHub Actions لا يعوض الاختبار الفعلي. لا تعتبر المنصة جاهزة لاستضافة أكواد غير موثوقة حتى تُفعّل project quotas لكل مجلد بوت ويثبت اختبار الشبكة والحصة والعزل على الخادم.

## الاختبارات
يوجد فحص تلقائي عبر GitHub Actions عند كل تحديث على فرع `main` أو عند فتح Pull Request. نجاح هذا الفحص لا يثبت عزل عمليات البوتات ولا يختبر تشغيل بوت Discord حقيقي.
